# План: Личные финансы (PFM)

> Этот план — живой документ. До тех пор, пока MVP не написан, любой пункт можно пересмотреть.

## 1. Что это и для кого

Личный финансовый менеджер для одного человека. Не просто трекер расходов, а полная картина финансов:

- несколько банковских карт и счетов;
- вклады с процентами и сроками;
- портфель акций;
- кредиты с остатком и графиком платежей;
- ежемесячные подписки;
- регулярные обязательства (аренда, алименты, налоги и т. п.).

**Главная особенность workflow:** пользователь не вносит операции руками. Он пишет мне (агенту) текстом или скидывает скрины выписок — я парсю и вношу данные через CLI/API. Приложение используется для просмотра, аналитики и редких корректировок.

## 2. Архитектура

Три слоя, связанных через REST API:

```
┌─────────────┐    скрины/текст     ┌──────────────┐
│  Пользователь│ ─────────────────► │   Агент       │
└─────────────┘                    │  (Mavis)      │
                                   └──────┬────────┘
                                          │ CLI / API
                                          ▼
┌─────────────┐     REST API       ┌──────────────┐
│  UI          │ ◄───────────────► │  Бэкенд      │
│  (браузер)   │                   │  Node + DB   │
└─────────────┘                   └──────────────┘
```

1. **Агент (Mavis)** — принимает текст/скрины, парсит их в структурированный JSON, вызывает CLI или REST API бэкенда. Парсинг отчётов — задача агента, не приложения.
2. **Бэкенд** — Node.js + Express + SQLite, единая точка истины. Отдаёт REST API для UI и принимает команды от CLI агента.
3. **UI** — SPA в браузере. Показывает данные, позволяет корректировать (если агент ошибся), управлять категориями и справочниками.

Бэкенд работает локально на машине пользователя (позже — на домашнем сервере). UI открывается в браузере по `http://localhost:3000` (или аналогично).

## 3. Стек

| Слой | Технология | Почему |
| --- | --- | --- |
| Бэкенд | Node.js + Express | Минимум зависимостей, понятно, легко расширять |
| БД | SQLite (better-sqlite3) | Один файл, бэкап = копия файла, не нужен отдельный сервер БД |
| CLI | Node-скрипт | Дёргает REST API или пишет в БД напрямую |
| UI (вариант A) | Vanilla JS + ESM-модули + CSS | Без сборки, минимальный оверхед |
| UI (вариант B) | React + Vite + TypeScript | Удобнее при росте UI; добавляет инструменты |

Для MVP рекомендую **вариант A**. Если UI станет сложным — мигрируем на B без потери данных (модели и API не меняются).

## 4. Модели данных

Все суммы — целые копейки. Все ID — UUID v4. Все даты — ISO (`YYYY-MM-DD` или `YYYY-MM-DDTHH:mm:ssZ`).

### Account — банковский счёт / карта
| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | uuid | |
| `name` | string | Например, «Tinkoff Black» |
| `bank` | string | Банк выпуска |
| `type` | enum | `debit`, `credit`, `card`, `savings` |
| `currency` | string | `RUB` на старте |
| `balance` | integer | **Зафиксированный** остаток в копейках на дату `balanceAsOf` |
| `balanceAsOf` | date? | Дата фиксации остатка, ISO `YYYY-MM-DD`. `NULL` = фиксации нет (прежнее инкрементальное поведение) |
| `currentBalance` | integer | Вычисляемое: реальный остаток = `balance` + операции после `balanceAsOf` (в БД не хранится) |
| `color` | string | Цвет в UI |
| `archived` | boolean | |
| `createdAt`, `updatedAt` | datetime | |

**Почему так.** Баланс счёта в приложении не может быть «просто числом»: операции вносит агент, часть истории подтягивается выписками, а часть — нет. Поэтому хранится *снимок* (`balance` на дату `balanceAsOf`), а реальный остаток считается как снимок плюс всё, что произошло после даты снимка. Операция, попавшая в уже зафиксированный период, отклоняется с 409 (см. «Сверка остатков» ниже) — иначе она посчиталась бы дважды.

## 5. Workflow ввода данных

### Сценарий A — текст в чате
> «Тинькофф блэк, снял 1500 в Магните 10 сентября»

Агент парсит, видит:
- account = «Tinkoff Black»
- amount = −1500 ₽
- category = «Продукты»
- date = 2026-09-10

Вызывает CLI и подтверждает: «Записал: 1500 ₽, Продукты, Tinkoff Black, 10 сентября. Ок?»

### Сценарий B — скриншот
Пользователь скидывает скрин из приложения банка или брокера. Агент читает через image-analysis / vision, извлекает операции/позиции, вносит пачкой.

### Сценарий C — длинный текст или голос
> «У меня ещё вклад в Сбере 500к под 8% годовых с капитализацией, открыт в марте, до конца года. И кредит в Альфе на 800к под 12%, плачу 15 тысяч в месяц 15 числа»

Агент парсит, создаёт/обновляет Deposit и Loan.

### Сценарий D — выписка PDF (опционально)
Если пользователю удобнее — он может скинуть PDF выписку, агент распарсит через pdf skill. Но это не автоматизированный поток, а разовая помощь.

### Сверка остатков и ретро-операции
Из выписок приходит не вся история, поэтому у счёта есть **зафиксированный остаток**: `balance` + `balanceAsOf` (дата, на которую он верен). Реальный остаток = `balance` + операции с датой **строго позже** `balanceAsOf` (день фиксации включён в снимок).

Сверка — это когда пользователь говорит «на карте сейчас 12 345,67 ₽»:

```bash
fin agent reconcile-account --account "Tinkoff Black" --balance 12345.67 [--as-of 2026-09-14]
# API: POST /api/accounts/<id>/reconcile { "actualBalance": 1234567, "asOf": "2026-09-14" }
```

`GET /api/accounts/<id>/reconcile` — превью без записи: что зафиксировано, сколько операций после даты фиксации и какой остаток получается сейчас.

**Ретро-операция.** Если агент приносит операцию с датой внутри зафиксированного периода (`date <= balanceAsOf`), API отвечает `409`:

```json
{
  "error": "retro_transaction",
  "accountName": "Tinkoff Black",
  "date": "2026-09-10", "balanceAsOf": "2026-09-14",
  "balance": 1230000, "currentBalance": 1234567,
  "hint": { "options": [
    { "action": "reconcile",          "method": "POST",  "path": "/api/accounts/<id>/reconcile", "body": { "actualBalance": 1234567, "asOf": "2026-09-14" }, "effect": "операция уже учтена в зафиксированном остатке — повторно вносить её не нужно" },
    { "action": "move_balance_as_of", "method": "PATCH", "path": "/api/accounts/<id>",           "body": { "balanceAsOf": "2026-09-09" },                        "effect": "фиксация сдвинется, операция попадёт в расчёт как новая" }
  ] }
}
```

Дата операции нормализуется в календарный день до проверки: `date` вида `2026-09-15T01:00:00+04:00` принимается и сохраняется как `2026-09-15` (день, как его записал клиент, без пересчёта в UTC), а дата, из которой день не извлекается (`10.09.2026`), отклоняется `400 invalid_date` — гейт 409 и формула `currentBalance` сравнивают уже нормализованный день, обойти 409 битой датой нельзя.

Разрешается одним из двух способов (оба отражены в `hint.options`):

1. **Сверка** — если фактический остаток изменился, ввести актуальный: `balance := факт`, `balanceAsOf := дата`.
2. **Сдвиг фиксации** — `PATCH /api/accounts/<id> { "balanceAsOf": "<день раньше операции>" }`. Зафиксированный остаток пересчитывается так, чтобы реальный остаток не изменился. `balanceAsOf: null` снимает фиксацию (`balance := реальный остаток`).

Ручная правка `balance` без `balanceAsOf` трактуется как сверка на сегодня. Счета, созданные до появления этой модели, живут с `balanceAsOf = NULL`: проверка не применяется, реальный остаток равен `balance`, сверка доступна в любой момент.

## 6. CLI для агента (черновик)

```bash
# Счета
fin agent add-account --name "Tinkoff Black" --bank tinkoff --type debit --currency RUB --balance 100000
fin agent list-accounts
fin agent reconcile-account --account "Tinkoff Black" --balance 12345.67
fin agent update-account --account "Tinkoff Black" --as-of 2026-09-01

# Транзакции (одна или пачка)
fin agent add-transaction --account "Tinkoff Black" --type expense --amount 1500 --category "Продукты" --date 2026-09-10
fin agent add-transactions --file transactions.json

# Вклады
fin agent add-deposit --bank sber --name "Накопительный" --principal 500000 --rate 8 --opened 2026-03-01 --capitalization --payout end

# Акции
fin agent add-holding --broker t-invest --ticker SBER --quantity 100 --avg-price 250 --currency RUB
fin agent update-holding --id <id> --quantity 150 --avg-price 248

# Кредиты
fin agent add-loan --bank alfa --name "Потреб" --principal 800000 --rate 12 --monthly 15000 --payment-day 15 --type consumer

# Подписки
fin agent add-subscription --name "Яндекс Плюс" --amount 299 --period monthly --next 2026-10-01

# Обязательства
fin agent add-obligation --name "Аренда" --amount 30000 --period monthly --next 2026-10-05 --recipient "Иванов"

# Отчёты
fin agent show --month 2026-09
fin agent net-worth
```

Конкретные имена флагов и формат JSON оформим по ходу реализации.

## 8. Котировки акций

- **Российские**: MOEX ISS (https://iss.moex.com) — публичный, без ключа. Тикеры вида `SBER`, `GAZP`, `FXRU`.
- **Зарубежные**: Yahoo Finance через `yahoo-finance2` (npm). Тикеры вида `AAPL`, `MSFT`.

Котировки обновляются:
- При открытии дашборда портфеля (с кэшем 15 минут);
- По кнопке «Обновить».

Если у пользователя только российские — MOEX хватит. Если смесь — добавляем Yahoo.

## 10. Открытые вопросы

Не блокеры, но стоит решить до старта Phase 1:

- **Котировки**: российские, зарубежные, или смесь? (от этого зависит, подключаем ли Yahoo.)
- **Multi-currency**: пока только рубли? Если у пользователя есть счета в USD/EUR — нужна конвертация (по курсу ЦБ).
- **Хостинг бэкенда**: только локально на ноутбуке, или планируется на домашнем сервере (мини-ПК, Raspberry Pi)?
- **Сколько всего единиц**: примерное число карт, вкладов, акций, кредитов. (Нужно для UI — нужна ли пагинация, виртуализация списков.)
